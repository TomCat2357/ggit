# Googleドキュメント単体で動くGit風バージョン管理ツール 設計仕様書

**版**: 0.1（ドラフト）
**対象**: 単一のGoogleドキュメント内で、タブをブランチに見立てたGit風バージョン管理を行うコンテナバインド型ツール

---

## 1. 概要

本書は、単一のGoogleドキュメント内で、タブをブランチに見立てたGit風のバージョン管理を実現するツールの設計仕様をまとめたものである。コンテナバインドのGoogle Apps Script（GAS）を中核とし、外部リポジトリや追加サービスに依存せず、**対象ドキュメント単体で完結する**ことを目標とする。

提供する操作は、明示的なコミット（チェックポイント）、ブランチ（タブ）、差分表示、合流（マージ）であり、これらをカスタムメニューからGUI操作できるようにする。

---

## 2. 背景と動機

### 2.1 ネイティブ変更履歴の限界

Googleドキュメントは自動的にバージョンを保存しているが、Git的な版管理としては次の3点が欠けている。

- **線形性**: 履歴がタイムライン構造であり、DAG（分岐・合流）を持たない。
- **粒度**: 版管理の単位がドキュメント全体であり、タブ／セクション単位で扱えない。
- **コミット段階の不在**: 自動保存スナップショットが時間軸で並ぶのみ。`ファイル > 変更履歴 > 現在の版に名前を付ける`は、この線形タイムラインへの手動タグに過ぎず、ステージングやコミットのような明示的な確定操作が存在しない。

加えて、版情報がUIの奥に埋もれており、任意の版どうしの差分確認も煩雑である。

> **ネイティブ版復元との併用に関する注意**: ネイティブの「この版に戻す」は**ドキュメント全体**を
> 巻き戻すため、メタストアを格納する `.vcs` タブ（§5.2 案A）も一緒に過去へ戻り、それ以降の
> コミット履歴が失われる。本ツールはこれに耐えるため、メタストアを PropertiesService にも
> バックアップする（§5.2 / §5.4）。

### 2.2 設計方針

Docsの「常時自動保存・明示的チェックポイント無し」という性質は、Gitのステージングよりも jj（Jujutsu）の "working copy が常にコミット" に近い。本ツールはこの自動保存モデルを土台に、**名前付きノード（コミット）** と **ブランチ（タブ）** を付与する設計とする。

## 3. 概念マッピング（Git → 本ツール）

本実装は Jujutsu 流のモデルへ寄せている（付録C）。対応表は jj 概念を併記する。

| Git / jj の概念 | 本ツールでの対応 |
| --- | --- |
| リポジトリ | 対象ドキュメント |
| 作業ツリー | 編集中の単一タブ（作業タブ） |
| 現在地（jj の `@`／作業コピー） | `store.working`（現在地のコミットID＝匿名ヘッド） |
| ブランチ（jj の bookmark） | `.vcs` ストア内の参照（ブックマーク名 → コミットID）。commit では自動前進しない（付録C） |
| コミット | 作業タブ本文のスナップショット＋メタ情報 |
| スタッシュ | `objects` 内の `stash:true` 付き仮コミット（付録C） |
| オブジェクトストア／コミットグラフ | メタタブ（`.vcs`）またはサイドカーJSON |
| タグ | 自前メタデータ（必要に応じてネイティブ名前付き版を併用） |
| コミットID | 本文シリアライズの SHA-256 短縮ハッシュ |

## 4. システム構成

### 4.1 コンポーネント

- **コンテナバインドGAS**: 対象ドキュメントに紐づくスクリプト本体。`onOpen` でカスタムメニューを生成する。
- **メタストア**: コミットグラフ（オブジェクトストア）を保持する領域。配置は §5.2 を参照。
- **差分／マージエンジン**: テキストレベルの diff・3-way マージを担う（diff-match-patch を移植）。

### 4.2 タブ操作のAPI前提

- **読み取り**: `getTabs()` がTabのリストをDictで返し、`Tab.asDocumentTab().getBody().getText()` で各タブ本文を取得できる。子タブは `Tab.getChildTabs()` で再帰的に辿り、全タブを走査する。アクティブタブは `Document.getActiveTab()` で取得する。
- **タブ生成**: `DocumentApp` 本体にタブ追加メソッドは無いが、Docs API の `documents.batchUpdate` に `addDocumentTab` リクエストが用意されているため、**Docs拡張サービス経由**で新規タブ（ブランチ）を生成できる。

> 補足: 上記タブ系メソッドはタブ機能（2024年後半導入）に対応した比較的新しいAPI面であり、利用前に現行ドキュメントで挙動確認すること。

## 5. データ設計

### 5.1 コミットオブジェクト

各コミットは以下のスキーマでシリアライズする。

```jsonc
{
  "id":        "a1b2c3d",        // 本文シリアライズの SHA-256 短縮ハッシュ
  "parent":    "9f8e7d6",        // 親コミットID（初回コミットは null）
  "parent2":   null,             // マージ第2親（マージコミットのみ。通常コミットは null）
  "message":   "見出し構成を整理",
  "author":    "tomo",
  "timestamp": "2026-06-14T12:00:00+09:00",
  "payload":   {                 // 親との差分 or フルスナップショット
    "type": "delta",             // "full" | "delta"
    "data": "H4sIAAAA..."        // gzip+Base64
  },
  "stash":     true              // 任意。スタッシュ（仮コミット）のみ true（付録C）。通常コミットは省略
}
```

- **コミットID**: `Utilities.computeDigest(SHA_256, ...)` で算出し短縮する。入力は `parent / timestamp / 本文`（jj モデルではブランチ所有概念が無いため `branch` は入力に含めない）。
- **親ポインタ**: `parent` により祖先チェーン＝DAGを形成する。
- **`branch` フィールドの廃止**: jj 流モデル（付録C）への移行に伴い、コミットはブランチを所有しない。グラフ上の枝は `parent`/`parent2` の DAG とブックマーク／現在地から導出する。
- **`stash`（拡張）**: スタッシュを「コミットだけどスタッシュだと分かる」形で表すため、仮コミットに `stash:true` を付ける（付録C）。
- **`parent2`（拡張）**: 本実装では合流（マージ）を表現するため、コミットスキーマに第2親 `parent2` を追加した。通常コミットでは `null`、マージコミットでのみマージ元の HEAD を指す。これにより `parent`／`parent2` を辿って真の DAG を構成できる。
- **payload（拡張）**: 本実装では full/delta を判別するため `{ "type", "data" }` の構造化形式とした。`type` が `"full"` のときは本文全文、`"delta"` のときは親コミットとの差分（diff-match-patch パッチテキスト）を保持し、いずれも `Utilities.gzip` + Base64 で圧縮する（Gitのpacked deltasと同等の発想）。

### 5.2 オブジェクトストアの配置（3案比較）

| 案 | 配置 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A** | メタタブ（`.vcs`）にJSON格納 | ドキュメント単体で完結 | 人間による誤編集リスク、ドキュメント肥大 |
| **B** | PropertiesService（ドキュメントプロパティ） | スクリプト管理で隠蔽できる | 合計約500KB上限で実用文書には不足 |
| **C** | 同一フォルダのサイドカーJSONファイル | 堅牢・大容量 | 「ドキュメントのみで完結」から逸脱 |

**推奨**: 差分保存＋gzip圧縮を前提に、まず案Aを基本とする。肥大が問題化した場合に案Cへ移行する設計余地を残す。本実装は案Aを基本としつつ、**ネイティブ版復元への耐性のため案B（PropertiesService）をバックアップとして併用するハイブリッド**を採用する（§5.4）。

### 5.3 容量対策

- スナップショットは差分保存を基本とし、一定間隔でフルスナップショット（基準点）を挿入してリストア時の差分連鎖を短く保つ。
- payloadはgzip圧縮して格納する。

### 5.4 ネイティブ版復元への耐性（ハイブリッド・バックアップ）

§2.1 のとおり、ネイティブ版復元（`ファイル > 変更履歴 > この版に戻す`）は**ドキュメント全体**を巻き戻す。案A（メタストアを `.vcs` タブに格納）では、これにより `.vcs` タブも過去状態へ戻り、**それ以降のコミット履歴が失われる**。

本実装はこれを防ぐため、メタストアを **PropertiesService（DocumentProperties）にも二重保存**する。DocumentProperties は**ドキュメント本文ではない**ため、ネイティブ版復元の影響を受けず最新状態を保つ。これを「正」とし、巻き戻しを検知して履歴を復旧する。

- **世代カウンタ `gen`**: ストアに単調増加の整数 `gen` を持たせ、保存（`Ggit_storeSave`）ごとに +1 する。`gen` はコミットID計算（tabId/parent/ts/snap）にも payload にも関与しないため、ハッシュ・復元・後方互換は不変。
- **二重書き込み**: 保存時は **PropertiesService（バックアップ）→ `.vcs` タブ**の順で同じストアを書く。Properties を先に書くことで「タブが巻き戻っても Properties は常に最新」という不変条件を担保する。バックアップは best-effort（容量超過等でも `.vcs` タブ保存は継続し、警告のみ返す）。
- **巻き戻し検知と採用**: 読込時（`Ggit_storeLoad`）はタブと Properties の両方を読み、`Ggit_pickStore` が `gen` の大きい方を採用する。`backup.gen > tab.gen` はネイティブ版復元のシグナルであり、この場合バックアップを正として履歴を復旧する。
- **遅延ヒール / 明示ヒール**: 読込時はタブへ書き戻さない（読み取り経路の副作用・Docs API クォータを避ける）。採用された新しいストアは次回保存でタブ＋Properties 両方へ書かれ自動的に整合する（遅延ヒール）。復元直後に確実に整合させたい場合は、メニュー「整合性チェック / 復旧」で即時にタブをバックアップから書き戻せる（明示ヒール）。
- **挙動（重要）**: 本機構は**作業タブ本文の巻き戻しを取り消すものではない**。ネイティブ復元で本文は過去に戻るが、ggit の**コミットグラフ（履歴・各ブランチ HEAD）は保全される**。復元後に編集して commit すると、保全された最新 HEAD を親に新コミットが積まれる（＝Git で過去内容を HEAD 上にコミットし直すのと同じく、履歴は線形に保たれ消えない）。
- **容量**: PropertiesService は値 ~9KB/件・合計 ~500KB の上限。ストアを gzip+Base64 して ~8KB チャンクに分割保存する。上限超過時はバックアップ保護が縮退する（タブ保存は継続）ため、その規模では案C（Drive サイドカー）への移行余地を残す。
- **スコープ**: `PropertiesService.getDocumentProperties()` は追加 OAuth スコープ不要（`appsscript.json` は変更なし）。

## 6. コマンド仕様（カスタムメニュー）

`onOpen` で生成するメニュー項目と挙動。

| コマンド | 挙動 |
| --- | --- |
| **commit(message)** | アクティブタブ本文をスナップショット化。親＝現在地 `working`、新コミットを記録し、**`working` のみ前進**。ブックマークは動かさない（付録C）。 |
| **bookmark set/delete(name)** | ブックマーク（名前付きポインタ）を任意のコミット（既定＝現在地）に設定/移動/削除する（`jj bookmark set` 相当）。タブは生成しない（付録B/C）。 |
| **goto(target)** | `target`（ブックマーク名 or コミットID）へ現在地 `working` を移動。作業タブ本文をその内容で置き換え、未コミット内容はスタッシュ（仮コミット）へ退避する（旧 checkout）。 |
| **log()** | コミットDAGをブランチ（分岐）を意識した ASCII レーングラフで表示（フラット表示にも切替可）。`@`＝現在地、`<name>`＝ブックマーク、`[stash]`＝スタッシュ。各行にメッセージ・作者・日時（タイムゾーンは非表示）を表示し、上部に現在地 `@hash`／そのブックマーク／メッセージ／作者を表示する。**行クリックでコミットを選択**し、下部の操作パネルから goto / merge / bookmark / diff を実行する。クリック地点からルートまでの直線（第1親チェーン）だけに絞る「直線表示」チェックボックスを備える。 |
| **diff(commitA, commitB)** | 2コミット間のテキスト差分を表示（log 画面の操作パネルから A・B を選択して実行）。 |
| **merge(source)** | `source`（ブックマーク名 or コミットID）を現在地 `working` へ3-wayマージ。衝突は本文へマーカー書き戻し。`working` のみ前進。log 画面で選択コミットを「@へマージ」して実行する。 |
| **stash pop/drop(id)** | スタッシュ（仮コミット）を作業タブへ戻して消す（pop）／破棄する（drop）。 |

> **UI 統合（実装メモ）**: diff・bookmark・merge・goto はいずれも **log（グラフ）画面を操作ハブ**として、行を選択しその場で実行する形に集約した（diff/bookmark/merge の独立メニュー項目は廃止。goto は専用ダイアログも残す）。コマンドのモデル・データ構造（§5 / 付録C）は不変で、変更は UI 層のみ。commit が記録する `author`（メールアドレス, §5.1）を log の各行と現在地ヘッダに表示する。

## 7. 差分とマージ

### 7.1 差分

- **diff-match-patch**（Neil Fraser, プレーンJS）をGASへ移植して用いる。
- `getText()` で取得したタブ本文どうしのテキスト差分を算出・表示する。

### 7.2 マージ（3-way）

- 共通祖先（マージベース）コミットを基準に、diff-match-patch の `patch_apply` で3-wayマージを実行する。
- 衝突箇所には Git 同様のマーカー（`<<<<<<<` / `=======` / `>>>>>>>`）を対象タブへ書き戻し、手動解決させる。

### 7.3 制約

- リッチテキスト（見出し・表・書式）を伴う差分・マージは信頼性の担保が困難。**テキストレベルを優先**し、構造要素は段階的対応とする。

### 7.4 書式の記録・復元（スコープ①）

差分・マージはプレーンテキスト対象のまま据え置く一方、**スナップショット（記録）と復元は書式に対応する**。

- **保存形式**: payload に格納する素材を、プレーンテキストから構造化 JSON 文字列へ拡張する。

  ```jsonc
  { "v":1, "text":"<body.getText() と一致する全文>",
    "fmt": { "runs":[{ "s","e","a" }], "paras":[{ "i","a" }] } }
  ```

  - `text` は従来のプレーン全文に一致し、diff / merge はこの `text` を射影（`Ggit_plainOf`）して使うため**プレーン処理は不変**。
  - `fmt` を比較に含めることで、**テキスト同一・書式のみ変更**を commit が検知できる。
  - 圧縮 / delta / フル間隔 / コミットID は文字列処理なので、この JSON 文字列をそのまま流用する（**無改修**）。
- **後方互換**: 旧 `.vcs`（payload が生プレーンテキスト）も `Ggit_parseSnap` / `Ggit_plainOf` が透過的に読む。
- **キャプチャ/復元**: 文字書式は `Body.editAsText()` の属性区間、段落書式は段落系要素の属性として取得し、復元は `setText` 後に `setAttributes` で再適用する（batchUpdate の index 計算に依存しない）。
- **フィデリティ境界（①）**: 文字書式（太字／斜体／下線／取消線／フォント／サイズ／前景色・背景色／リンク）と段落書式（見出し＝NamedStyle／配置／インデント／行間／段落前後スペース）に対応。**表・画像・リストのグリフ／ネストは非対応**（テキストとしては保持するが書式は復元しない）。diff / merge の書式対応（②③）は引き続き段階的対応とする。

## 9. 既知の制約・リスク

- **checkout**: 単一の作業タブ内でブランチを切り替えるモデルへ変更（付録B）。プログラムからのタブ切替制約は、作業タブ本文をその場で置き換えることで回避する。複数の作業タブ運用は想定しない（操作対象は常にアクティブタブ1枚）。
- **同時編集**: 複数コラボレータ編集時、スナップショットの一貫性に注意（batchUpdateの原子性はあるが、自動保存との競合に留意）。
- **肥大化**: フルスナップショット多用時のドキュメント／ストア肥大。差分保存と圧縮で緩和。
- **リッチテキストのマージ**: 書式・表の合流は信頼性を担保しにくく、テキスト優先とする。

## 付録A. 本実装による仕様拡張点

設計ドラフト（§1〜§10）に対し、実装にあたり次の最小限の拡張を加えた。

1. **コミットスキーマへの `parent2` 追加（§5.1）**: マージコミットで第2親を保持し、DAG の合流を表現可能にした。
2. **payload の構造化（§5.1）**: `{ "type": "full" | "delta", "data": <gzip+Base64> }` とし、フルスナップショットと差分を明示的に判別できるようにした。

その他の設計方針（案A採用、差分＋圧縮、テキスト優先など）はドラフトのままである。

## 付録B. ブランチモデルの変更（タブ＝ブランチ → 単一タブ＋ストア内ブランチ）

当初は「タブ＝ブランチ」とし、branch 時に `addDocumentTab` で新タブを生成して内容を複製する設計だった（§3 / §6 ドラフト）。しかし GAS では次の制約により実用が困難だった。

- **アクティブタブをプログラムから切り替えられない**（§9）。checkout がUI操作前提となり、操作が分かりにくい。
- **同一ドキュメントの複数インスタンス同時書き込み問題**: `addDocumentTab`（Docs API）で生成した新タブへ `DocumentApp.openById` 経由で本文を書き込むと、`getActiveDocument()` 側の `.vcs` 保存とフラッシュが競合し、**新タブ本文の書き込みが失われて空になる**不具合が発生した。

そこで本実装では「**単一の作業タブ＋ストア内ブランチ**」モデルへ変更した（Git の「1つの作業ツリー＋複数ブランチ」と同型）。

- ブランチは `.vcs` ストアの `branches`（ブランチ名 → HEADコミットID）と `head`（現在ブランチ名）で表現する。新タブは生成しない。
- `branch(name)` は現HEADを指す参照を作って切り替える（履歴＝祖先チェーンを共有して引き継ぐ）。
- `checkout(name)` は作業タブ本文を対象ブランチHEADの内容（テキスト＋書式）でその場で置き換える。未コミット内容はスタッシュへ退避する。
- `merge` は現在のブランチへ取り込む。現在がマージ元の祖先なら早送り（fast-forward）し、分岐していれば3-wayマージして `parent2` 付きマージコミットを記録する。
- 全書き込みが `getActiveDocument()` の単一インスタンスに閉じるため、上記の競合は原理的に発生しない。
- **後方互換**: 旧スキーマ（version 1: `branches` が `tabId → {head, name}`）の `.vcs` は読み込み時に自動移行する（`Ggit_migrateStore`）。タブ名をブランチ名に採用し、同名は連番で一意化する。

> 注: 本付録の「ストア内ブランチ（version 2）」モデルは、付録C の Jujutsu 流ブックマークモデル（version 3）へさらに発展した。version 2 の `.vcs` も読み込み時に version 3 へ自動移行する。

## 付録C. Jujutsu 流ブックマークモデルへの移行（version 2 → version 3）

付録B の「単一作業タブ＋ストア内ブランチ（Git 流の名前付きブランチが commit で自動前進）」を、より Docs の自動保存モデルに馴染む **Jujutsu（jj）流のブックマークモデル**へ変更した。動機は §2.2（Docs は jj の "working copy が常にコミット" に近い）の延長である。

### C.1 現在地（`working`）と匿名ヘッド

- 現在地を「ブランチ名」ではなく **コミットID `store.working`**（jj の `@`＝匿名ヘッド）で表す。
- `commit` は新コミットを作って **`working` のみを前進**させる。これにより「A→B→C で B に戻って B→D」のように、名前を付けなくても複数の匿名ヘッド（葉）が自然に生まれ、グラフ（付録C.4）で枝として可視化される。
- `goto(target)` は `working` を任意のコミット／ブックマークへ移動し、作業タブ本文をその内容で置き換える（旧 `checkout`）。

### C.2 ブックマーク（手動の名前付きポインタ）

- ブランチを **ブックマーク**（`store.bookmarks`：名前 → コミットID）に置き換えた。`jj bookmark` と同様、**commit では自動で動かず**、`bookmark set/move/delete` で明示的に操作したときだけ移動する。
- これにより「どこに名前を付けるか」をユーザーが制御でき、無名の試行（匿名ヘッド）を気軽に残せる。

### C.3 スタッシュ＝仮コミット（`stash:true`）

- スタッシュを DAG の外（旧 `store.stashes[]`）ではなく、**`objects` 内の `stash:true` 付き仮コミット**として記録する（要望：「コミットだけどスタッシュだと分かるようにコミット」）。親は退避時の現在地 `working`。
- **no-op ガード**: 退避前に、現在の内容が履歴上のいずれかのコミット/スタッシュと一致するか判定し、一致する場合は既に保存済みで上書きしても失われないため仮コミットを作らない（`Ggit_stashIfNeeded`）。判定は**テキストベース**（`Ggit_plainOf`）で行い、書式のみ異なる場合も「同じ内容」とみなして退避しない（テキスト＋書式まで見る `commit` の「変更がありません」とは異なり、ここはテキスト一致のみで判定する）。
- **戻す（pop）**＝スタッシュ内容を作業タブへ戻し、`working` をその親へ移し、**仮コミットを削除**する（要望：「そこに戻ったらスタッシュを消す」）。**破棄（drop）**は内容を戻さず削除する。
- グラフ上はスタッシュも匿名ヘッドの一種として `[stash]` 付きで現れる。

### C.4 ブランチを意識したグラフ表示

- `log` は `parent`/`parent2` の DAG から **`git log --graph` 風の ASCII レーングラフ**を生成する（`Ggit_collectNodes` → `Ggit_graphLines`、いずれも純粋関数で SelfTest 検証）。分岐は collapse（`|/`）、マージは sprout（`|\`）で描く。フラット（時系列）表示にも切替できる。

### C.5 データモデルと後方互換

- ストア構造（version 3）:
  ```jsonc
  { "version": 3,
    "objects":   { "<id>": <commitObj> },   // 通常コミット＋スタッシュ（stash:true）
    "bookmarks": { "<name>": "<commitId>" }, // 手動ポインタ
    "working":   "<commitId>" }              // 現在地 @（未確立なら null）
  ```
- **自動移行**（`Ggit_migrateStore`、純粋関数）: version 2 の `branches`→`bookmarks`、`head`（ブランチ名）→`working`（そのコミットID）、`stashes[]` 各要素→`stash:true` 付きコミットへ変換。version 1 も従来どおり正規化を経て version 3 へ。コミットの旧 `branch` フィールドは読み飛ばす。
